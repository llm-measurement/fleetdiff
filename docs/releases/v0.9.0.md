# v0.9.0 Release Notes

**8 exported rows versus 9 daily requests: 1 missing row.** fleetdiff can now
compare your LiteLLM spend export with its daily request counts and identify
missing rows per UTC day. Token and spend totals stay exactly as recorded.

## Check Your Spend Log

Export `LiteLLM_SpendLogs` and `LiteLLM_DailyUserSpend` from the same application
and completed UTC days with the [paired export helper](../ROW_COVERAGE.md#export-and-compare),
then add the daily file to your usual comparison:

```sh
fleetdiff investigate --litellm-spend spend.csv \
  --litellm-daily-spend daily.csv --group-by key
```

The [checked synthetic fixture](../ROW_COVERAGE.md#reading-coverage) reproduces
a response-ID collision through the pinned LiteLLM proxy and database writers:

```text
Spend-log row coverage (relative to LiteLLM daily request counts):
  2026-10-07 UTC: 8 exported rows; 9 daily requests (8 successful, 1 failed); 1 missing row.
  2026-10-08 UTC: 1 exported row; 1 daily request (1 successful, 0 failed); counts match.
Token and spend totals below use exported rows only.
```

The check counts selected exported rows, including failures and call types
outside token analysis. It also works with single-period session-budget review.
JSON adds explicit per-day counts and status under `row_coverage`.

## Upgrade

Use the matching v0.9.0 SQL projection and `export-coverage.sh` helper. It exports
both tables in one read-only, repeatable-read transaction into a new private
directory. The daily CSV contains only dates and counts, without identities,
prompts or responses. Omit `--litellm-daily-spend` to retain the existing output
byte for byte; existing request exports and collector summaries keep working.

The internal import-helper refactor preserves v0.8.0 golden outputs and legacy
hash bytes.

## Limits

Use the same application scope, filters and retention for both exports, and
let asynchronous writes settle. The counter definitions are tested on LiteLLM
v1.104.0. Matching counts cannot detect requests omitted from both tables:
the runtime fixture demonstrates this with failure logging disabled. Successful
response-cache hits count even without a provider send. This checks recorded
rows, not billing, token completeness or the cause of a discrepancy. Missing
daily dates and partial-day coverage remain unknown; nothing is imputed.
